# v2.0 Groundwork — the "run it yourself" edition

_Planning brief, 2026-06-01. Forward-looking; nothing built yet. This is the
detailed companion to ROADMAP.md's v2.0 bucket._

## Thesis

v1.x is a polished pipeline for ONE league on MY Snowflake. v2.0's single
job is **portability**: runnable by anyone, for their league, on their own
machine, with no cloud accounts beyond a Google sign-in and no engineering.

**Acceptance test — the literal bar for "v2.0 done":** a tech-illiterate
father-in-law, over a phone call, gets it running for his league from his
own computer.

That test is the design oracle. Every "you'd just..." that assumes a GCP
console, a `.env` edit, a CLI flag, or a cloud warehouse is a v2.0 bug.

## The four pillars

### 1. Storage — get off Snowflake (DECIDED: DuckDB first)

Everything assumes Snowflake today: `output/db.py` (`snowflake.connector`),
`extract/extract.py`'s loader, dbt `profiles.yml` (`type: snowflake`), and
Snowflake-specific SQL across the models (`LATERAL FLATTEN`, `QUALIFY`,
`VARIANT` / `raw_json:` JSON access, `::` casts).

**DuckDB is the first target** — the only free, zero-account, runs-entirely-
local option, which IS the father-in-law test. Build the seam so
BigQuery / Postgres / Snowflake stay swappable adapters, not rewrites: DuckDB
proves the seam works, the others prove it generalizes. The live Snowflake
path must keep working.

### 2. Source — get off ESPN-only (REQUIRED this stage: CBS)

The extract is ESPN-specific: the espn-api wrapper + kona endpoints,
`ESPN_S2` / `SWID` cookies, and the box_scores / scoring_settings / roster /
draft JSON shapes that `stg_*` parse. **CBS support is a hard requirement for
v2.0**, not a maybe.

Add a **source-adapter layer** so ESPN and CBS feed the same RAW → staging
contract; nothing downstream of staging should know which platform it came
from. Expect the hardest unknowns of the whole effort here: CBS's data
shapes, its cookie/auth model, and the stat-ID mapping onto our
`stat_classification` seed.

> **Status 2026-07-07/08:** those unknowns are resolved. Spike verdict GO
> (MLB-13; browser-extracted token, reCAPTCHA rules out scripted login);
> the 2026 fantasy layer is captured + content-verified, the 2004–2025
> per-game archive is fully backfilled (MLB-44/45), and the site-UI
> league-history archive is captured too (MLB-47: standings +
> transactions back to 2001, year-end rosters 2003+, drafts 2017+,
> franchise overviews — cookie-authenticated raw HTML), all raw under

> warehouse load, CBS staging onto the contract, and the stat crosswalk —
> see CHANGELOG and docs/roadmap/multi-platform-support.md.

### 3. Bootstrap — the "father-in-law" layer

A guided one-command setup (PowerShell for Windows; weigh a cross-platform
path) that takes the user's cookies + league ID + platform (ESPN/CBS),
provisions the local DuckDB, and runs extract → dbt → outputs — with sane
defaults, a wizard for the unavoidable inputs (how to grab cookies from the
browser), readable errors, and ZERO manual `.env`/profiles editing. This is
where "tech-literate" stops being a prerequisite.

### 4. Output sharing & onboarding — keep shareable Sheets, kill the GCP setup

DECISION (maintainer): **keep the Google Sheets almanac.** It is the only
*shareable* output — a single link the whole league opens. A local HTML file
can't be shared without hosting it somewhere, and that hosting step is the
exact "deep technical navigation" the test forbids. (The BBCode recap is
already zero-cloud — paste it into the league forum — so this is purely an
*almanac* concern.)

Requiring a Google **account** is a fine bar. The barrier is the **setup**:
today each user must create a GCP project + an OAuth client in Google Cloud
Console (`GOOGLE_OAUTH_CLIENT_PATH`) — deeply technical, fails the test.
v2.0's job is to eliminate that. Investigate shipping ONE pre-configured
OAuth app (our client ID) so the user only does "sign in with Google → click
Allow," and assess the catches: Google's unverified-app warning, the
~100-test-user cap on unverified apps, and the app-verification process. A
local static-HTML almanac is a reasonable *offline/fallback* output but it
does NOT solve sharing, so it's secondary.

## Approach — plan first, don't build

The first v2.0 session produces:

- **Coupling audit** — every Snowflake-ism and ESPN-ism in one table:
  thing / file / coupling type / effort to abstract. Storage and source
  side by side.
- **Architecture decision doc** (`v2.0 Architecture.md`, or ROADMAP entries)
  for the three seams — storage adapter, source adapter, bootstrap + auth —
  in the project's phase-doc "options considered → chosen → rationale" style.
- **Phased roadmap.** Suggested build order: DuckDB parity → CBS source
  adapter → bootstrap wizard → Sheets-onboarding simplification. All four are
  required to pass the acceptance test; this is just sequence. Each phase
  independently shippable.
- **DuckDB spike.** Point the dbt project at a `duckdb` target over a sample
  of RAW, run it, and catalog exactly what compiles vs breaks. That one
  experiment de-risks pillar 1 more than any amount of planning — and tells
  us whether the storage seam is a weekend or a month.

## Constraints

- **Don't break the live Snowflake/ESPN weekly path** — it runs the real
  league every week.
- **Keep the dbt-portfolio quality** — this is still a showcase, and a clean
  adapter abstraction is itself a strong portfolio story.
- **Reuse existing conventions** — wide convergence facts, seed-as-config,
  the active/inactive split.
- **Snowflake SQL that can't be made portable goes behind dbt macros /
  adapter dispatch** (`{{ adapter.dispatch }}`, cross-db macros), never
  duplicated per-adapter.
